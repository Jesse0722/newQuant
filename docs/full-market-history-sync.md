# 全市场历史回补与数据源能力

T06 为全市场同步增加按数据源能力选择的历史回补路径。默认组合源使用逐股历史接口补齐本地缺失日期；有历史按日全市场能力时优先批量获取，再补未返回的股票。任务结果报告实际有数据的日期、目标清单覆盖率，以及来源不支持、空数据、失败和成功的情况。

本次实现没有对真实业务库发起批量回补，也没有自动启用新的供应商或购买权限。数据恢复仍需在运行服务中显式启动同步；已有不完整行的修复属于 T07/T08。

## 数据源选择

| 当前具体来源 | 历史按日全市场 | 逐股历史 | 本次回补选择 |
|---|---|---|---|
| Tushare | 支持 | 支持 | 仅已配置且有 token 时参与；优先按日请求 |
| BaoStock | 不支持 | 支持 | 保守声明 SH/SZ，逐股获取整个缺口日期区间 |
| AkShare | 当日快照，不是历史 | 支持 | 使用沪深京历史接口；同步专用 strict 模式保留异常，避免误报空数据 |
| Tencent | 不支持 | 支持，但窗口首行前收不完整 | 本次完整核心字段回补不使用，能力结果说明其限制 |

能力声明不等于接口实时可用或权限验收。任务开始时固定具体来源实例，运行中切换全局数据源不会改变已经启动的任务。只使用当前已配置的来源，不会因为某源失败而自动加入 Tushare。

新写入数据的内部单位为 `vol=手`、`amount=千元`。BaoStock 的股/元按声明转换；AkShare 历史的手/元转换成交额；Tushare 保持手/千元。每一条记录整体选择一个来源，不能从不同来源拼接同一条行情的字段。此转换只作用于本次新增数据，旧记录和其他同步入口的单位修复仍由 T07 处理。

接口口径依据：[Tushare daily 官方文档](https://tushare.pro/document/2?doc_id=27)、[AKShare 历史行情官方文档](https://akshare.akfamily.xyz/data/stock/stock_quote.html)。BaoStock 的静态声明依据现有适配器原样输出的 volume/amount 及其 API 口径；本轮只抽查免费源历史行情，不验证 Tushare 账户权限。

## 日期与目标清单

盘后窗口以上海时间 16:00 为界；盘中使用上一已完成交易日。优先使用明确版本的本地连续日历，2026 年参考日历见 [data_reference](../backend/data_reference/README.md)。跨年或本地日历范围不足时尝试已配置来源的日历；不足、过旧或报错时明确失败，不再用工作日填充节假日。

目标从本地 `stock_basic` 的当前股票主数据筛选，剔除代码规则不符、当前已退市和明确晚于目标日上市的证券。它是 `local_current_master_proxy`，不是历史点时证券池。缺少历史退市、类型和停牌状态时，`market_coverage_ratio` 始终为 `null`、`coverage_status=unverifiable`。代码规则仍有局限，不能用于认证证券类型。

首次使用且没有有效普通 A 股主数据时，尝试由已配置来源初始化清单，只新增通过代码规则的证券，不覆盖已有元数据。已有清单不会被本任务重新写入，也不能保证涵盖后来上市的所有股票；需在运行前确认清单新鲜度。

## 请求和写入

1. 每日先查询目标清单的已有主键。已有记录直接复用，不再为了判断“已存在”调用上游。
2. 只对缺失主键发请求。优先按日历史批量接口；返回不足时按股票历史区间回补，后备来源只补尚未取得的日期。
3. 核心字段、OHLC 次序、代码、日期、重复键和非有限值先校验；无效响应不能写入。
4. 仅新增缺失记录，不覆盖现有 OHLC、前收、涨跌幅、量额或换手率。已有异常记录进入 `repair_required_dates`，等待 T07/T08。
5. 每批写入失败先 rollback，后续股票仍可继续。成功批次已经提交，不因后续部分失败自动撤销。
6. 来源失败仅记录类型和目标，不把可能包含 token/代理地址的异常文本写入结果。默认每次请求至少等待 0.15 秒；Tushare 至少 1.25 秒，实际权限仍以账户为准。

没有缺失主键且当前清单核心字段有效覆盖达标时，任务直接 `complete` 且 `already_satisfied=true`，不发历史行情请求。已有行全都存在但质量不足时，不反复抓取后跳过，而是报告已有行待修复。

BaoStock/AkShare 的历史日线适配器原先先对空 DataFrame 赋 `ts_code` 标量，再填日期索引，会令返回行的股票代码为空。本次改为先建立源数据索引再赋值，并用多行身份与标准化测试覆盖。这只修正之后的返回结果，不能自动修复已存行情。

## API

```text
GET /api/sync/full-market/capabilities
POST /api/sync/full-market?days=5&end_date=20261104
GET /api/sync/status/{task_id}
```

能力接口只返回静态声明，不采集行情。`days` 仍为 1–250，默认 60；`end_date` 可省略。原有调用方式和任务类型保持兼容。任务具体结果同时保存到 `SyncLog.result`；日期解析/主数据失败等启动错误也持久化失败，且抛给后台任务包装器，防止被重新标记为完成。

数据管理页仍通过“全市场同步”启动任务。逐日表展示核心有效代码数、目标数和当前清单覆盖，明确显示真实市场覆盖率待验证。部分完成或存在来源告警时给出 warning。

## 结果口径

| 字段 | 含义 |
|---|---|
| `requested_dates` | 实际解析出的请求交易日，不是自然日或工作日猜测 |
| `data_dates` / `days_synced` | 处理后本地存在核心有效行情的日期，包含已存在数据 |
| `completed_dates` | 当前目标清单核心有效覆盖 ≥95% 的日期；不代表历史全市场完整 |
| `empty_dates` | 无有效本地数据且最终为空的日期；停牌原因未知，不自动认定漏采 |
| `empty_response_dates` | 日期任务中存在未补齐的空响应，可与覆盖达标同时存在 |
| `unsupported_dates` | 本地无有效数据且无合格来源的日期 |
| `failed_dates` | 存在未解决请求或写入失败的日期；整体部分完成时也可有值 |
| `repair_required_dates` | 已有主键阻止新增且核心数据不完整，需进入修复流程 |
| `date_results` | 逐日最终状态、目标覆盖、空/失败等遥测和来源计数 |
| `provider_attempts` | 各来源的成功/空/失败/不支持检查统计；能力跳过不产生网络调用 |
| `returned_sources` | 通过响应校验的来源行数，不等于写入贡献 |
| `inserted_sources` | 本次实际新增行的来源分布 |
| `skipped_sources` | 请求期间因主键已出现而跳过的来源行分布，不认证原行来源 |

`outcome` 为 `complete`、`partial`、`failed`、`no_data` 或 `unsupported`。最终覆盖达标可与空响应或恢复后的来源错误同时存在；来源质量告警独立显示，不把后备源已经补齐的数据误报为缺失。来源分布只是任务级计数，逐行血缘和原始修订审计仍属于 T08。

## 数据库与回退

没有 schema 变更或迁移。本次开发未对业务库执行同步。正式回补会新增行情与任务日志；运行前按 [数据库手册](development-postgresql.md)备份当前唯一主库。

本次提交的写入策略不删除、不覆盖既有行情，但已成功提交的新增批次没有自动撤销命令。若真实回补后发现来源或单位错误，应停用同步并走 T08 的审计修复/恢复流程，不通过按日期批量删除来回退。代码回退只恢复旧同步实现，不会自动撤销已经新增的数据。
